# Tạo framebuffer và tìm vị trí một pixel

## Vấn đề cần giải quyết

Bài 01 đã mở được cửa sổ, nhưng nền vẫn do SDL tô trực tiếp. Muốn tự vẽ, ta cần một bức ảnh nằm trong RAM và cho phép C++ sửa từng pixel. Bức ảnh đó là framebuffer.

Bài này chỉ làm phần bộ nhớ: tạo một vector, biết nó rộng/cao bao nhiêu và tìm đúng phần tử cho tọa độ `(x, y)`. Chưa cần học màu hoặc texture. Vì vậy, cửa sổ cuối bài vẫn xanh đen; kết quả mới được kiểm bằng số đọc, debugger và Canvas.

## Hiểu ý tưởng trước khi viết code

Đừng bắt đầu với 960×540. Hãy lấy ảnh rộng 4, cao 3:

```text title="12 phần tử, xếp từng hàng từ trái sang phải"
y = 0     [ 0] [ 1] [ 2] [ 3]
y = 1     [ 4] [ 5] [ 6] [ 7]
y = 2     [ 8] [ 9] [10] [11]
```

Vector không biết “hàng”. Nó chỉ có các phần tử từ 0 đến 11. Chúng ta tự đặt quy ước: lưu hết hàng trên rồi mới sang hàng dưới, gọi là row-major.

Muốn đến pixel `(2, 1)`, đi qua một hàng đủ 4 phần tử, rồi đi thêm 2:

$$index = y \times width + x = 1 \times 4 + 2 = 6$$

Góc phải dưới `(3, 2)` có index 11. Đi xuống một hàng làm index tăng đúng `width`, không phải `height`.

Sau một lần cấp phát thành công, ta phải giữ `pixels.size() == width × height`. Nếu chỉ đổi hai số kích thước mà quên vùng nhớ, công thức đúng vẫn có thể trỏ ra ngoài vector.

## Viết code từng bước

### Bước 1 — Tách dữ liệu ảnh khỏi SDL

Tạo `include/lab.hpp` với `#pragma once`, các include `algorithm`, `cstddef`, `cstdint`, `new`, `vector` và `namespace lab`. Bên trong, tạo `struct Framebuffer` có ba trường:

```cpp title="include/lab.hpp — dữ liệu của Framebuffer"
int width = 0;
int height = 0;
std::vector<std::uint32_t> pixels;
```

`uint32_t` là số nguyên không dấu 32 bit. Ở bài 03, bốn kênh màu sẽ nằm trong số ấy. Vector tự quản lý vùng nhớ liên tiếp và giải phóng khi framebuffer hết vòng đời.

`int` cho kích thước/tọa độ giúp giữ được số âm khi kiểm đầu vào. `std::size_t` là kiểu dùng cho kích thước/chỉ số của vector; chỉ chuyển sang nó sau khi đã loại đầu vào âm.

Framebuffer mới tạo đang rỗng, với width/height bằng 0. Ta chỉ dùng nó làm ảnh sau khi `resize` thành công.

### Bước 2 — Đặt giới hạn trước khi cấp phát

Thêm hằng số này trong struct:

```cpp title="include/lab.hpp — budget cấp phát"
static constexpr std::size_t maximumPixelCount = 16u * 1024u * 1024u;
```

Đó là 16.777.216 pixel, tương đương 64 MiB khi mỗi pixel chiếm 4 byte. Một ảnh 1920×1080 cần khoảng 7,9 MiB; đây không phải lý do để bỏ qua giới hạn hoặc lỗi cấp phát.

Ta sẽ tạo một vector mới rồi mới thay vector cũ. Trong thời gian đó, có thể tồn tại cả hai vùng nhớ, ngoài texture của SDL. Vì thế, giới hạn số pixel không phải tổng RAM cao nhất của cả chương trình.

### Bước 3 — Cấp phát thành công rồi mới đổi kích thước

Thêm method:

```cpp title="include/lab.hpp — Framebuffer::resize"
bool resize(int newWidth, int newHeight) {
    if (newWidth <= 0 || newHeight <= 0) {
        return false;
    }

    const std::size_t columns = static_cast<std::size_t>(newWidth);
    const std::size_t rows = static_cast<std::size_t>(newHeight);
    if (columns > maximumPixelCount / rows) {
        return false;
    }

    try {
        std::vector<std::uint32_t> newPixels(columns * rows, 0u);
        pixels.swap(newPixels);
    } catch (const std::bad_alloc&) {
        return false;
    }

    width = newWidth;
    height = newHeight;
    return true;
}
```

Có ba điểm đáng đọc chậm:

- Kiểm width/height dương trước. Nhờ vậy `rows` không thể bằng 0 khi làm phép chia.
- Kiểm `columns > maximumPixelCount / rows` trước khi nhân. Ta không cần tạo ra một tích quá lớn rồi mới phát hiện lỗi.
- `newPixels` được cấp phát trước; `swap` chỉ đổi vùng nhớ khi đã thành công. Nếu `std::bad_alloc` xuất hiện vì thiếu RAM, hàm trả false và ảnh cũ còn nguyên.

`try/catch` ở đây chỉ xử lý lỗi cấp phát, không phải cách che mọi lỗi của chương trình. Khi vector tạm ra khỏi scope, nó giải phóng vùng nhớ cũ nhận từ `swap`.

Khác với việc clamp về 1, hàm này từ chối ảnh 0×0 hoặc kích thước quá lớn. Người gọi phải quyết định chờ, báo lỗi hay thoát; framebuffer không tự đổi yêu cầu thành một kích thước khác.

### Bước 4 — Viết công thức index

Thêm ngay dưới `resize`:

```cpp title="include/lab.hpp — Framebuffer::index"
[[nodiscard]] std::size_t index(int x, int y) const {
    return static_cast<std::size_t>(y) * static_cast<std::size_t>(width) + static_cast<std::size_t>(x);
}
```

`const` nói rằng hàm không đổi dữ liệu ảnh. `nodiscard` nhắc khi gọi nhưng bỏ kết quả. Điều kiện dùng hàm là tọa độ đã hợp lệ; `index` không tự kiểm biên. Ta sẽ đặt việc bảo vệ vào `putPixel` ở bài sau.

Không gọi `index(-1, 0)` để “thử lỗi”. Chuyển −1 sang size_t tạo một số không dấu rất lớn, không còn là tọa độ âm dễ nhận ra.

### Bước 5 — Tạo framebuffer trong main

Thêm `#include "lab.hpp"` vào `src/main.cpp`. Sau khi window/renderer đã tạo thành công, thêm:

```cpp title="src/main.cpp — cấp phát ảnh ở checkpoint 2"
lab::Framebuffer framebuffer;
if (!framebuffer.resize(kInitialWidth, kInitialHeight)) {
    std::cerr << "Framebuffer allocation failed\n";
    SDL_DestroyRenderer(renderer);
    SDL_DestroyWindow(window);
    SDL_Quit();
    return EXIT_FAILURE;
}
std::cout << framebuffer.width << " x " << framebuffer.height << " = " << framebuffer.pixels.size() << " pixels\n";
```

Đây vẫn là ảnh thử có kích thước 960×540, chưa phải ảnh theo output high-DPI. Bài 03 sẽ đọc kích thước đầu ra thật khi tạo texture.

Build `project_1_checkpoint_2`, chạy và kiểm 518.400 phần tử trong terminal. Nếu mở debugger, xem `pixels.size()`; đừng kỳ vọng thay một phần tử sẽ đổi cửa sổ ngay vì vector chưa được gửi sang SDL.

## Ghép các phần lại

Tới đây có hai phần độc lập: SDL giữ cửa sổ sống, Framebuffer giữ vùng nhớ ảnh. `main` tạo chúng rồi chạy vòng lặp cũ; không có lời gọi upload nào bị giấu trong Framebuffer.

Tự tính lại ba vị trí `(0,0)`, `(0,1)`, `(3,2)` với ảnh 4×3. Sau đó đổi width thành 5 trong Canvas. Vì mỗi hàng dài thêm một phần tử, index của các hàng phía dưới thay đổi dù tọa độ bạn chọn không đổi.
