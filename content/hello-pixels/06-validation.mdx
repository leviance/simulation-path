# Kiểm chứng và chạy dự án hoàn chỉnh

## Vấn đề cần giải quyết

Nhìn thấy gradient không đủ để kết luận chương trình đúng. Có thể phần mép cuối chưa bao giờ đạt 255, một lần ghi ngoài biên chưa tình cờ crash, hoặc lỗi chỉ xuất hiện khi build Release.

Bài này không thêm scene thứ năm. Ta viết test cho dữ liệu thuần, kiểm đường upload/present bằng smoke hữu hạn, rồi dùng checklist desktop cho phần máy không tự chứng minh được. Cuối trang là toàn bộ mã nguồn của dự án và ZIP chứa starter, checkpoint, final cùng tests.

## Hiểu ý tưởng trước khi viết code

Có ba loại bằng chứng khác nhau:

| Cách kiểm | Chứng minh điều gì? | Không thay thế được |
| --- | --- | --- |
| CTest không mở cửa sổ | Màu, index, bounds, công thức ảnh, dữ liệu sau resize | Driver, hình ảnh thực và input |
| Smoke SDL ẩn, tự thoát | Tạo texture, resize, upload và present không báo lỗi | Cảm nhận trực quan, bàn phím/minimize thật |
| Kiểm trực tiếp desktop | Bốn scene, phản hồi input, DPI và vòng đời window | Đáp án số chính xác của thuật toán |

Test tốt có đáp án độc lập. Ví dụ ảnh 4×3 có index cuối 11 do ta tính tay, không gọi index một lần nữa để làm expected cho chính index.

Hàm `assert` có thể bị tắt khi định nghĩa NDEBUG ở Release. Ta dùng `check` tăng số lỗi và main trả EXIT_FAILURE, để test vẫn có hiệu lực ở cả hai cấu hình.

## Viết code từng bước

### Bước 1 — Tạo chương trình test thuần C++

Tạo `tests/tests.cpp`, include `lab.hpp` cùng các header chuẩn được dùng. Không include SDL. Thêm biến `int failures = 0;` và helper:

```cpp title="tests/tests.cpp — check không bị tắt ở Release"
void check(bool condition, std::string_view label) {
    if (condition) {
        return;
    }
    std::cerr << "FAILED: " << label << '\n';
    ++failures;
}
```

Một lỗi không làm test dừng ngay, nên bạn thấy các nhóm lỗi liên quan. Cuối main, trả kết quả cho CTest:

```cpp title="tests/tests.cpp — mã thoát của test"
if (failures != 0) {
    std::cerr << failures << " validation check(s) failed\n";
    return EXIT_FAILURE;
}
std::cout << "All Project 01 validation checks passed\n";
return EXIT_SUCCESS;
```

Source đầy đủ tách testMemoryAndBounds và testScenes thành hai hàm để main không thành một khối dài. Các helper chỉ phục vụ việc đọc test, không thay công thức cần kiểm.

### Bước 2 — Kiểm index và lần ghi ngoài biên

Những kiểm tra đầu tiên:

```cpp title="tests/tests.cpp — fixture ảnh 4×3"
lab::Framebuffer framebuffer;
check(framebuffer.resize(4, 3), "create 4 by 3");
check(framebuffer.pixels.size() == 12, "4 by 3 owns 12 pixels");
check(framebuffer.index(0, 0) == 0, "top-left index");
check(framebuffer.index(3, 0) == 3, "last column in first row");
check(framebuffer.index(0, 1) == 4, "next row advances by width");
check(framebuffer.index(3, 2) == 11, "bottom-right index");
```

Sau khi clear bằng màu nền và lưu bản sao before, thử cả bốn phía:

```cpp title="tests/tests.cpp — các tọa độ phải bị bỏ qua"
framebuffer.putPixel(-1, 0, marker);
framebuffer.putPixel(0, -1, marker);
framebuffer.putPixel(4, 0, marker);
framebuffer.putPixel(0, 3, marker);
framebuffer.putPixel(INT_MIN, INT_MAX, marker);
check(framebuffer.pixels == before, "outside writes do not change any element");
```

Biến marker có màu `rgba(1,2,3,4)`, khác nền. Sau đó ghi hợp lệ ở (3,2), kiểm phần tử 11 và đếm đúng một phần tử mang marker. Cách này mạnh hơn việc chỉ nhìn chương trình “không crash”.

### Bước 3 — Kiểm resize bị từ chối không phá ảnh cũ

Sau khi lưu pixels thành saved:

```cpp title="tests/tests.cpp — giữ state khi resize thất bại"
check(!framebuffer.resize(0, 3), "reject zero width");
check(!framebuffer.resize(4, -1), "reject negative height");
check(!framebuffer.resize(INT_MAX, INT_MAX), "reject huge product before allocation");
check(!framebuffer.resize(INT_MAX, 1), "reject width above memory budget");
check(framebuffer.width == 4 && framebuffer.height == 3, "failed resize preserves dimensions");
check(framebuffer.pixels == saved, "failed resize preserves pixels");
```

Kích thước quá lớn bị chặn trước allocation; bài test không tìm cách dùng hết RAM máy bạn. Ngoài ra, source chạy 100 kích thước nhỏ liên tiếp rồi ghi vào phần tử cuối để kiểm công thức sau mỗi resize.

Test này kiểm state khi đầu vào bị từ chối. Nó không giả vờ đã ép hệ điều hành tạo ra mọi tình huống thiếu RAM hoặc lỗi GPU; các đường lỗi ấy vẫn cần xử lý trong code.

### Bước 4 — Dùng đáp án biết trước cho cả bốn scene

- Solid: mọi phần tử bằng đúng màu đã yêu cầu.
- Gradient 3×3: bốn góc đạt các cặp R/G 0 hoặc 255; giữa là 127/127. Có thêm ảnh 1×1, 1×3, 3×1.
- Checker cell=2: pixel trong cùng ô cùng màu, ô ngang bên cạnh khác màu, ô chéo cùng màu. Cell 0/âm theo quy tắc clamp về 1.
- Noise seed=17: sáu giá trị đầu biết trước là 62, 210, 117, 76, 182, 85. Vẫn kiểm cùng seed giống nhau và đổi seed khác nhau.

Màu được kiểm thêm lúc biên dịch:

```cpp title="tests/tests.cpp — bit packing"
static_assert(lab::rgba(255, 0, 0) == 0xFF0000FFu);
static_assert(lab::rgba(1, 2, 3, 4) == 0x01020304u);
static_assert(lab::rgba(0, 0, 0, 0) == 0u);
static_assert(lab::rgba(255, 255, 255, 255) == 0xFFFFFFFFu);
```

Đừng chỉ tạo noiseA/noiseB bằng cùng hàm rồi so sánh: một hàm sai nhưng xác định vẫn vượt qua cách kiểm đó. Fixture độc lập mới phát hiện thay đổi không mong muốn trong công thức.

### Bước 5 — Build và chạy CTest ở cả hai cấu hình

CMake trong ZIP đã có target tests, include final/include và đăng ký project_1_validation; test không link SDL. Tại thư mục project:

```bash title="Terminal — kiểm Debug và Release"
cmake -S . -B build -DBUILD_CHECKPOINTS=ON
cmake --build build --config Debug --parallel 2
ctest --test-dir build -C Debug --output-on-failure --timeout 20
cmake --build build --config Release --parallel 2
ctest --test-dir build -C Release --output-on-failure --timeout 20
```

Với Ninja/Makefiles một cấu hình, dùng hai build directory và -DCMAKE_BUILD_TYPE=Debug/Release. Không chạy -C Release rồi nghĩ đã đổi một binary Debug thành Release.

`--parallel 2` giới hạn công việc compile; `--timeout 20` chặn từng test treo. Trong repository website, các suite còn có process supervisor và deadline tổng. Không bỏ deadline chỉ vì một lần chạy lâu hơn dự kiến.

### Bước 6 — Kiểm đường SDL bằng smoke hữu hạn

Final có thêm helper runSmoke trong `include/smoke.hpp`. Đó là công cụ test riêng: cửa sổ ẩn, 12 lần đổi kích thước và luân phiên bốn công thức qua đúng các helper upload/present. Nó tự kết thúc, không chạy vòng tương tác vô hạn.

Main chỉ chọn đường này khi nhận `--smoke`:

```cpp title="src/main.cpp — chọn đường smoke"
if (smoke) {
    success = lab::runSmoke(window, renderer);
} else {
    success = runPixels(window, renderer);
}
```

Biến smoke được đọc từ argv; chạy bình thường không có tham số vẫn mở ứng dụng tương tác. Trên Windows:

```powershell title="Terminal — SDL smoke và chạy tương tác"
.\build\Debug\project_1_final.exe --smoke
.\build\Release\project_1_final.exe --smoke
.\build\Debug\project_1_final.exe
```

Nếu chạy qua automation, đặt hard timeout bên ngoài khoảng 15 giây cho mỗi smoke. Một lời gọi driver vẫn có thể kẹt; giới hạn số vòng lặp không thay thế deadline của process.

## Ghép các phần lại

Bản hoàn chỉnh có các trách nhiệm rõ ràng:

- lab.hpp sở hữu pixel và công thức thuần C++.
- presentation.hpp tạo/copy texture và thay cặp tài nguyên.
- main.cpp giữ vòng đời SDL, event, tham số scene và dirty.
- smoke.hpp chỉ dành cho đường kiểm hữu hạn.
- tests.cpp chứa fixture, không mở window.

Từ phím 2, bạn phải lần được tới gradient, tới rgba/putPixel/index, tới upload/pitch rồi tới cửa sổ. Từ một test thất bại, bạn phải biết kiểm phần CPU hay presentation thay vì sửa mò cả chương trình.

## Thử làm sai để hiểu đúng

1. Đổi expected index cuối từ 11 thành 12. CTest phải fail cả Debug lẫn Release; sửa lại expected, không sửa code đúng để chiều theo test sai.
2. Đổi một hệ số LCG hoặc đảo kênh R/B. Fixture phải phát hiện.
3. Bỏ lời gọi present trong một bản thử. CTest CPU vẫn đạt: điều đó giải thích vì sao checklist SDL/desktop còn cần thiết.
4. Giữ bounds check, thử các tọa độ ngoài ảnh qua Lab và CTest. Không cần bỏ hàng rào bảo vệ để cố gây lỗi bộ nhớ.

## Tự kiểm tra kết quả

- [ ] CTest đạt ở Debug và Release, không dùng assert cho runtime validation.
- [ ] Bốn scene đều có fixture kiểm dữ liệu, không chỉ kiểm số phần tử.
- [ ] Smoke tự thoát; không nhầm smoke ẩn với kiểm trực tiếp desktop.
- [ ] Phím 1–4, N và −/= hoạt động ở scene tương ứng.
- [ ] Resize ít nhất 10 lần; minimize/restore; kiểm high-DPI nếu có thiết bị.
- [ ] Close và Escape thoát sạch.
- [ ] Bạn tự giải thích được index, color packing, pitch, dirty và thời điểm hủy texture.

## Bài tập mở rộng

1. Xuất framebuffer thành file PPM để kiểm ảnh không phụ thuộc SDL.
2. Thêm fixture seed=0 và seed lớn nhất của uint32_t.
3. Đo số lần tạo ảnh/upload khi không có input để xác nhận dirty đang tiết kiệm công việc.
4. Thêm một scene mới và một test có đáp án tự tính trước.
