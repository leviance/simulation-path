# Đưa hai mảng Vec4 vào ba SSBO

## Bài toán của chúng ta

CPU đã có A/B, còn GPU chưa có dữ liệu để đọc. Ta cần ba vùng nhớ: hai input và một output. Đây là SSBO — Shader Storage Buffer Object — chứ không phải một texture hay vertex buffer dùng để vẽ.

Bài này chỉ cấp phát và upload. Không dùng hình dashboard để suy ra GPU đã tính; chưa có lệnh dispatch nào ở checkpoint 3.

## Hiểu ý tưởng trước khi viết code

Một Vec4 gồm bốn float 32 bit liên tiếp. `sizeof(Vec4)` và `alignof(Vec4)` đều được khóa ở 16; mảng `vec4[]` trong `std430` có stride 16 byte. Phần tử i bắt đầu tại byte `i*16`.

Buffer name là số driver trả qua `GenBuffers`. Binding 0/1/2 là vị trí shader tìm buffer; hai loại số này không đồng nghĩa. Shader khai báo A ở binding 0 thì C++ phải gắn đúng A vào vị trí đó, bất kể tên buffer là 7 hay 42.

## Bắt tay vào code

### 1. Khai báo hợp đồng layout và binding

Trong shader, khai báo ba block cùng hợp đồng layout:

```glsl title="shaders/vector_ops.comp — ba storage blocks"
layout(std430, binding = 0) readonly buffer InputA {
    vec4 inputA[];
};

layout(std430, binding = 1) readonly buffer InputB {
    vec4 inputB[];
};

layout(std430, binding = 2) writeonly buffer Output {
    vec4 outputData[];
};
```

`readonly` và `writeonly` mô tả cách shader dùng block; chúng không tự sao chép dữ liệu. C++ vẫn phải tạo, cấp và upload đủ byte.

### 2. Chuẩn bị sentinel và vùng canary

`prepareBuffers` kiểm size/budget trước allocation, tạo bản host có N+256 phần tử, rồi dùng `BufferData` cấp storage. Sau mỗi lần cấp, code đọc lại `GL_BUFFER_SIZE` và kiểm GL error; chỉ có buffer name khác 0 chưa chứng minh allocation thành công.

```cpp title="include/vector_compute_engine.hpp — giá trị ban đầu của output"
const float sentinel = std::numeric_limits<float>::quiet_NaN();
unwritten_.assign(paddedCount, guardValue());
std::fill_n(unwritten_.begin(), elementCount_, Vec4{sentinel, sentinel, sentinel, sentinel});
readback_.resize(paddedCount);
```

Đầu tiên gán canary cho cả vùng, sau đó chỉ thay N phần tử hợp lệ bằng NaN. Nhờ thứ tự này, padding không bị lẫn với output chưa ghi. `readback_` có cùng số phần tử để bài 6 đọc đủ cả hai vùng.

### 3. Upload rồi nối đúng binding

```cpp title="include/vector_compute_engine.hpp — upload và nối binding"
const std::array<const Vec4*, 3> data{paddedA_.data(), paddedB_.data(), unwritten_.data()};
for (GLuint binding = 0; binding < 3; ++binding) {
    api.BindBuffer(GL_SHADER_STORAGE_BUFFER, buffers_[binding]);
    api.BufferSubData(GL_SHADER_STORAGE_BUFFER, 0, byteCount(), data[binding]);
    api.BindBufferBase(GL_SHADER_STORAGE_BUFFER, binding, buffers_[binding]);
}
api.BindBuffer(GL_SHADER_STORAGE_BUFFER, 0);
requireNoGlError(api, "SSBO upload");
```

Hai input có canary trong padding. N output hợp lệ chứa NaN sentinel để nhận ra phần tử chưa được ghi; 256 output sau N chứa canary để nhận ra ghi quá N. Sentinel và canary không phải cùng một phép kiểm. CPU reference chỉ tính N phần tử, không đưa padding vào phép toán.

Việc cấp phát nằm ngoài các sample timing sau này. Nhưng mỗi sample vẫn upload A/B và reset output bằng `BufferSubData`; nhãn end-to-end sẽ bao gồm các lần truyền này.

## Chạy checkpoint

Build và chạy `project_37_checkpoint_3`. Dữ liệu CPU vẫn hiển thị; worker phải hoàn tất upload mà không có GL error. GPU output chưa readback nên không được hiển thị như đã xác nhận đúng.

## Thử làm sai để hiểu đúng

1. Trên Canvas, đọc byte offset của index 1 và 2: phải là 16 và 32, không phải 4 và 8. Thử tính bằng `index*sizeof(float)` để thấy vì sao cách đó chỉ đi qua một component chứ chưa qua một Vec4.
2. Trong shader fixture, đổi binding Output từ 2 sang 3. Bài sau sẽ dùng reflection để bắt lỗi interface trước dispatch; không chấp nhận một buffer chưa được nối chỉ vì shader compile thành công.

## Tự kiểm tra kết quả

- Vec4 có size/alignment 16 byte; buffer đủ N+256 phần tử.
- A/B/output dùng đúng binding, không dùng buffer name làm binding index.
- Allocation/upload lỗi không được báo là thành công.
- Checkpoint chưa dispatch; không đọc NaN sentinel rồi gọi đó là kết quả GPU.
