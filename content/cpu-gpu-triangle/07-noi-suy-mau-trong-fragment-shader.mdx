# Nội suy màu trong fragment shader

## Vấn đề cần giải quyết

Tam giác đang có một màu cố định. Dữ liệu VBO thực ra đã chứa ba màu khác nhau ở A, B, C; bài này cho phép chúng xuất hiện trên bề mặt. Nhấn C sẽ đổi cả hai phía giữa solid và smooth.

Bạn cần tách hai việc: quyết định pixel có nằm trong tam giác không, rồi mới tính màu của pixel đó. Trên CPU ta tính barycentric weights. Trên GPU, rasterizer nội suy dữ liệu giữa các đỉnh trước khi fragment shader nhận nó.

## Hiểu ý tưởng trước khi viết code

Với một điểm bên trong, ba barycentric weights cộng lại gần 1. Tại một đỉnh, weight của đỉnh đó gần 1; tại centroid, cả ba gần 1/3. Màu RGB được trộn theo ba hệ số ấy.

Vertex shader đặt clip w = 1 cho cả ba đỉnh, nên phép nội suy smooth ở đây tương ứng với nội suy affine của CPU. Khi học mesh perspective có w khác nhau, cần perspective-correct interpolation; đừng mang nguyên giả định 2D này sang mọi bài 3D.

## Viết code từng bước

### Bước 1 — Tính weights từ signed area

Tiếp tục hàm barycentricAtPoint trong include/pipeline.hpp. Mảng tam giác của hàm này chứa ScreenVertex sau phép đổi viewport, không phải các GpuVertex thô trong VBO. signedArea được tính bằng edge; nếu gần 0 thì ba đỉnh thẳng hàng hoặc trùng nhau, ta trả kết quả không có coverage trước khi chia:

```cpp title="include/pipeline.hpp — barycentric weights"
const float signedArea = edge(triangle[0].position, triangle[1].position, triangle[2].position);
if (!std::isfinite(signedArea) || !std::isfinite(point.x) || !std::isfinite(point.y) || std::abs(signedArea) <= 1.0e-8F) {
    return {};
}
const float weight0 = edge(triangle[1].position, triangle[2].position, point) / signedArea;
const float weight1 = edge(triangle[2].position, triangle[0].position, point) / signedArea;
const float weight2 = edge(triangle[0].position, triangle[1].position, point) / signedArea;
const float epsilon = 1.0e-6F;
const bool inside = weight0 >= -epsilon && weight1 >= -epsilon && weight2 >= -epsilon;
```

Tại centroid, ba weights gần `1/3`; tại một vertex, weight tương ứng gần `1` và hai weight còn lại gần `0`.

### Bước 2 — CPU nội suy ba channels bằng cùng weights

```cpp title="include/pipeline.hpp — smooth color"
Color color{0.38F, 0.68F, 0.94F};
if (smoothColor) {
    color = {
        triangle[0].color.red * weight0 + triangle[1].color.red * weight1 + triangle[2].color.red * weight2,
        triangle[0].color.green * weight0 + triangle[1].color.green * weight1 + triangle[2].color.green * weight2,
        triangle[0].color.blue * weight0 + triangle[1].color.blue * weight1 + triangle[2].color.blue * weight2,
    };
}
```

Coverage không đổi khi bật smooth mode. Chỉ nhánh chọn color thay đổi.

### Bước 3 — GPU nhận varying đã nội suy

```glsl title="Fragment shader — solid hoặc smooth"
in vec3 vColor;
uniform int uSmoothColor;
out vec4 fragmentColor;

void main() {
    vec3 solidColor = vec3(0.38, 0.68, 0.94);
    vec3 selectedColor = solidColor;
    if (uSmoothColor != 0) {
        selectedColor = vColor;
    }
    fragmentColor = vec4(selectedColor, 1.0);
}
```

Fragment shader không tự tính barycentric weights trong project này. Rasterizer phần cứng nội suy `vColor` theo vị trí fragment.

Tất cả vertex của bài này có clip w = 1, nên phép nội suy smooth tương ứng với công thức barycentric affine đang dùng trên CPU. Khi chuyển sang các vertex có w khác nhau, cần xét nội suy perspective-correct; đừng mặc định công thức 2D hiện tại đủ cho mọi mesh 3D.

### Bước 4 — So sau RGBA8 quantization

CPU float color được `putPixel` làm tròn thành byte. GPU framebuffer cũng dùng channels hữu hạn. Sai khác hợp lý không phải bằng 0 tuyệt đối ở float; bound cơ bản của một lần làm tròn là nửa bước `1/255` mỗi channel.

Giới hạn nửa bước ấy áp dụng cho **một lần** đổi float sang byte. Khi so hai kết quả CPU/GPU đã được lượng tử hóa riêng, còn có sai số phép tính và vị trí lấy mẫu. Vì vậy bài readback dùng quy trình so cùng tâm pixel và ngưỡng công bố riêng, thay vì áp nhầm giới hạn của một phép làm tròn cho cả hai pipeline.

## Ghép các phần lại

Cùng bool smoothColor được truyền vào rasterizeCpuTriangle và gpuTriangle.draw. Phím C đổi bool này; các hàm coverage không được thay đổi theo mode màu. C++ tự tính màu, còn GLSL nhận vColor đã nội suy.

Hãy chạy solid trước, bật smooth sau. Nếu hình dạng đổi theo C, lỗi không nằm ở một phép pha màu thông thường: kiểm nhánh truyền state, dữ liệu đầu vào hoặc giá trị không hữu hạn.

## Thử làm sai để hiểu đúng

Chỉ thay một chi tiết mỗi lần trên bản thử nghiệm. Ghi dự đoán trước, chạy để quan sát rồi phục hồi mã đúng trước khi đi tiếp.

1. Cho ba vertex cùng đúng màu solid (0.38, 0.68, 0.94). Bật/tắt C: gradient biến mất và hai mode phải cho cùng màu.
2. Giữ position, đổi màu của riêng A. Quan sát vùng gần A đổi nhiều nhất; centroid không đủ để phát hiện mọi lỗi hoán đổi màu giữa các đỉnh.

## Bài tập mở rộng

1. Thêm chế độ hiển thị riêng từng weight thành grayscale.
2. Đặt cả ba vertex color bằng đúng màu solid `(0.38, 0.68, 0.94)`; solid và smooth phải cho cùng màu. Nếu chọn một màu chung khác màu solid, hai chế độ vẫn khác nhau dù smooth không còn gradient.
3. Thử `flat` qualifier trong GLSL và giải thích provoking vertex quyết định màu nào.

Bài sau sẽ đọc fragment thật từ GPU bằng `glReadPixels` và thiết kế probe tránh tam giác edges.
