# Đọc lại GPU và đo sai khác

## Vấn đề cần giải quyết

Ta đã có hai hình chuyển động và nội suy màu giống nhau bằng mắt. Bài này thêm phép kiểm có số liệu: nhấn P để đọc một pixel GPU thật bằng `glReadPixels`, rồi so với màu CPU dự đoán tại đúng vị trí ấy.

Cẩn thận: centroid là một điểm hình học liên tục, không nhất thiết là tâm pixel. Nếu CPU tính màu tại centroid nhưng GPU trả màu ở tâm pixel lân cận, chính phép kiểm đã tạo sai số. Vì thế ta chọn pixel chứa centroid, tìm lại tâm của pixel đó, rồi mới tính màu tham chiếu.

## Hiểu ý tưởng trước khi viết code

Readback dùng bottom-left pixel coordinates và phải chạy sau draw, trước swap hoặc overlay. CPU expected color được làm tròn sang RGBA8 trước khi so. Ngưỡng sai số (tolerance) công bố là 2/255 trên channel có sai khác lớn nhất, không phải epsilon chung cho tọa độ và màu.

Centroid thường nằm trong nội thất, nhưng với tam giác rất nhỏ hoặc gần suy biến, tâm pixel được chọn vẫn có thể chạm cạnh. Đừng gắn nhãn PASS/FAIL hình học ở một probe chưa đủ khoảng cách tới edge. Fixture nghiệm thu dùng tam giác có kích thước xác định và kiểm dải cạnh riêng.

Bản hoàn chỉnh đo khoảng cách từ tâm pixel tới ba đoạn cạnh theo đơn vị pixel. Trong dải 1,5 pixel, cửa sổ báo `EDGE - NO VERDICT` thay vì tự kết luận PASS/FAIL; mẫu nền xa cạnh được ghi rõ `BACKGROUND`. Chưa bấm P thì trạng thái là `not measured`, không phải một sai số bằng 0.

## Viết code từng bước

### Bước 1 — Tạo probe từ geometry, không từ pixel đoán mò

```cpp title="include/pipeline.hpp — triangleCentroid"
inline Vec2 triangleCentroid(
    const std::array<GpuVertex, 3>& triangle,
    const Transform2D& transform
) {
    const std::array<GpuVertex, 3> transformed = transformedTriangle(triangle, transform);
    return {
        (transformed[0].positionX + transformed[1].positionX + transformed[2].positionX) / 3.0F,
        (transformed[0].positionY + transformed[1].positionY + transformed[2].positionY) / 3.0F,
    };
}
```

Probe xoay/dịch cùng tam giác vì được tính sau transform. Nó không bị bỏ lại ở vị trí cũ khi animation chạy.

### Bước 2 — Đổi NDC sang GPU pixel bằng viewport phải

```cpp title="include/pipeline.hpp — chọn pixel và tìm lại tâm mẫu"
inline ProbePixel locateProbePixel(Vec2 point, const Viewport& viewport) {
    if (viewport.width <= 0 || viewport.height <= 0 ||
        !std::isfinite(point.x) || !std::isfinite(point.y) ||
        point.x < -1.0F || point.x >= 1.0F || point.y < -1.0F || point.y >= 1.0F) {
        return {};
    }
    const Vec2 windowPoint = ndcToGpuWindow(point, viewport);
    const int x = int(std::floor(windowPoint.x));
    const int y = int(std::floor(windowPoint.y));
    const Vec2 center = gpuWindowToNdc({float(x) + 0.5F, float(y) + 0.5F}, viewport);
    return {true, x, y, center};
}
```

Đặt `ProbePixel` và helper này trong include/pipeline.hpp, bên cạnh các phép đổi viewport. `ProbePixel` giữ valid, x, y và centerNdc; xem khai báo đầy đủ trong source checkpoint. Trong readGpuProbe, gọi helper trước khi đọc GPU; nếu valid là false thì trả report chưa hợp lệ, không cố ép tọa độ vào mép cửa sổ.

Không đảo Y ở đây. `glReadPixels` dùng tọa độ cửa sổ với gốc bottom-left. Điểm cần chú ý là tọa độ hình học ban đầu hiếm khi trùng tâm pixel. Ví dụ viewport 100 × 100: NDC (0,0) rơi vào pixel (50,50), nhưng tâm pixel đó là (50,5; 50,5), tức NDC (0,01; 0,01). Nếu tính màu CPU ở (0,0) rồi so với pixel GPU, chính phép kiểm đã tạo ra sai lệch. Vì vậy ta đổi **tâm pixel được đọc** về NDC để tính màu kỳ vọng.

### Bước 3 — Đọc đúng một pixel

```cpp title="include/gpu_renderer.hpp — glReadPixels probe"
std::array<std::uint8_t, 4> pixel{};
api.ReadPixels(result.pixelX, result.pixelY, 1, 1, GL_RGBA, GL_UNSIGNED_BYTE, pixel.data());
if (api.GetError() != GL_NO_ERROR) {
    result.valid = false;
    return result;
}
result.actual = {
    float(pixel[0]) / 255.0F,
    float(pixel[1]) / 255.0F,
    float(pixel[2]) / 255.0F,
};
```

Readback có thể buộc CPU chờ GPU. Vì vậy final chỉ chạy đoạn này khi người dùng bấm `P`, không gọi trong mọi frame.

### Bước 4 — So output cùng representation

CPU expected color được `quantizeRgba8` trước khi so. Report in expected, actual và maximum difference; timing không liên quan đến pass/fail ở đây.

Trong readGpuProbe, sau khi kiểm pixelLocation.valid, tính phần tham chiếu bằng chính centerNdc vừa tìm được:

Cho `expectedColor` nhận màu nền trước. Nếu tâm pixel nằm trong tam giác theo oracle CPU, thay nó bằng màu nội suy; cuối cùng mới lượng tử hóa sang RGBA8. Đọc theo thứ tự này sẽ thấy rõ rằng ngoài tam giác cũng có một màu kỳ vọng cần kiểm, không phải một mẫu được bỏ qua.

```cpp title="include/gpu_renderer.hpp — màu kỳ vọng tại đúng tâm pixel"
result.valid = true;
const BarycentricSample expectedSample = sampleTriangleAtNdc(triangle, transform, pixelLocation.centerNdc, smoothColor);
result.inside = expectedSample.inside;
const Color background{11.0F / 255.0F, 16.0F / 255.0F, 32.0F / 255.0F};
Color expectedColor = background;
if (expectedSample.inside) {
    expectedColor = expectedSample.color;
}
result.expected = quantizeRgba8(expectedColor);
result.pixelX = pixelLocation.x;
result.pixelY = pixelLocation.y;
```

Nếu tâm mẫu nằm ngoài tam giác nhưng vẫn trong viewport, màu kỳ vọng là màu nền chung của hai panel, không phải màu nội suy kéo dài ra ngoài tam giác. Nếu centroid đã ra ngoài viewport, báo không có probe thay vì đọc một pixel cạnh rồi gọi đó là kết quả tại centroid.

Tham số `triangle` của readGpuProbe mặc định là kSourceTriangle ở checkpoint này. Khi thêm khả năng chỉnh vertex trong bài cuối, ta truyền mảng đang được chỉnh vào cùng hàm, để phần kiểm không âm thầm so với tam giác ban đầu.

## Ghép các phần lại

Phím P chỉ đặt probeRequested. Sau khi vẽ tam giác GPU, main gọi readGpuProbe đúng một lần rồi hạ cờ; đọc xong mới vẽ chữ và swap. Không gọi glReadPixels mỗi frame vì readback có thể buộc CPU chờ GPU.

Report phải có pixel được đọc, expected, actual, maximum difference và trạng thái hợp lệ. Điểm ra ngoài viewport không được ép vào mép ảnh. Điểm trong viewport nhưng ngoài tam giác được so với màu nền, không với màu nội suy kéo dài ra ngoài.

```bash title="Terminal — build và chạy checkpoint 08"
cmake --build build --config Debug --target project_33_checkpoint_8 --parallel 2
./build/Debug/project_33_checkpoint_8.exe
```

Đường chạy trên dành cho Visual Studio trên Windows. Với Ninja, chọn CMAKE_BUILD_TYPE khi configure và chạy executable ngay trong build, không có thư mục Debug/Release trung gian. Mọi checkpoint và final đều nằm trong cùng ZIP; bạn không cần Node.js để build C++.

## Thử làm sai để hiểu đúng

Chỉ thay một chi tiết mỗi lần trên bản thử nghiệm. Ghi dự đoán trước, chạy để quan sát rồi phục hồi mã đúng trước khi đi tiếp.

1. Trong viewport 100×100, tính pixel chứa NDC (0,0), rồi tính NDC của tâm pixel ấy. So (0,0) với (0.01,0.01) để thấy vì sao phải snap trước khi tính màu.
2. Trong bản thử nghiệm, đọc trước draw thay vì sau draw. Report có thể nhận nền hoặc frame trước; đưa readback về đúng vị trí rồi chạy lại. Không biến một kết quả tình cờ đúng thành bằng chứng.
