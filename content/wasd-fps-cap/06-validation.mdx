# Kiểm chứng và chạy bản hoàn chỉnh

## Vấn đề cần giải quyết

Bản tương tác đã có đủ chức năng. Bây giờ ta cần trả lời cụ thể: đúng ở đâu, sai thì test nào phát hiện, và còn phần nào phải thử trực tiếp?

Test thuần C++ kiểm công thức, input mapping, số pixel và thời gian nghỉ. Native smoke kiểm một đường chạy SDL hữu hạn. Không test nào trong hai loại đó chứng minh người dùng giữ WASD trên desktop đã hoạt động đúng; việc này vẫn cần thử bằng tay.

Trước khi xem đáp án, tự dự đoán: 150 bước 1/30 s đi bao xa? Frame dài 0,2 s làm mất bao nhiêu thời gian? Tô hình 34×34 cần bao nhiêu pixel? Frame làm việc 20 ms ở cap 60 nên nghỉ bao lâu?

## Hiểu ý tưởng trước khi viết code

Các đáp án tương ứng là 900 px, 0,15 s, 1.156 pixel và 0 ns. Những con số này kiểm tra các phần khác nhau, không thể thay bằng một câu “ứng dụng chạy mượt”.

<InteractiveLab demo="motion" mode="motion-validation" />

Canvas dùng cùng công thức và cùng giới hạn dt với C++; nó giúp bạn đối chiếu số đo trước khi chạy chương trình. Nó không biên dịch hoặc chạy source C++ trong trình duyệt.

Đặc biệt, test phải gọi **đường vào mà ứng dụng thật dùng**. Nếu test gọi normalize nhưng ứng dụng quên normalize khi đọc phím, test vẫn có thể xanh. Vì vậy ta đưa A/D/W/S vào `directionFromKeys`, giống `readDirection` của ứng dụng.

## Viết code từng bước

### Bước 1 — Tạo hàm check vẫn chạy ở Release

`tests/tests.cpp` có một chương trình console riêng, không link SDL. Phần hỗ trợ:


```cpp title="tests/tests.cpp — check không phụ thuộc NDEBUG"
namespace {
int failures = 0;

bool nearlyEqual(double left, double right, double epsilon = 1e-8) {
    return std::abs(left - right) <= epsilon;
}

void check(bool condition, std::string_view label) {
    if (condition) {
        return;
    }
    std::cerr << "FAILED: " << label << '\n';
    ++failures;
}
} // namespace
```


So số thực bằng sai số nhỏ vì những phân số như 1/30 không biểu diễn chính xác tuyệt đối trong nhị phân. `check` in nhãn lỗi và tăng bộ đếm. Cuối main, có lỗi thì trả `EXIT_FAILURE`; không lỗi thì `EXIT_SUCCESS`. Không dùng `assert` cho các điều kiện nghiệm thu, vì Release có thể định nghĩa `NDEBUG` làm assert biến mất.

### Bước 2 — Kiểm bàn phím trước, rồi kiểm quãng đường


```cpp title="tests/tests.cpp — input đi qua đúng hàm ứng dụng gọi"
const lab::Vec2 right = lab::directionFromKeys(false, true, false, false);
    const lab::Vec2 opposed = lab::directionFromKeys(true, true, true, true);
    const lab::Vec2 diagonal = lab::directionFromKeys(false, true, true, false);
    check(nearlyEqual(right.x, 1.0) && nearlyEqual(right.y, 0.0), "D points right");
    check(nearlyEqual(lab::length(opposed), 0.0), "opposite keys cancel");
    check(nearlyEqual(lab::length(diagonal), 1.0), "keyboard diagonal has unit length");
    check(diagonal.x > 0.0 && diagonal.y < 0.0, "W+D points up-right");
    check(nearlyEqual(lab::length(lab::normalize({})), 0.0), "zero direction stays finite");
```


Đây chưa phải test SDL nhận phím vật lý; nó xác nhận bốn giá trị bool được chuyển thành hướng đúng. Thử nhấn phím trực tiếp sẽ kiểm phần còn lại.

Tiếp theo tạo ba dãy tổng đúng năm giây:


```cpp title="tests/tests.cpp — mỗi dãy có cùng thời gian nhưng khác số bước"
std::array<double, 150> thirtyFps{};
    thirtyFps.fill(1.0 / 30.0);
    std::array<double, 300> sixtyFps{};
    sixtyFps.fill(1.0 / 60.0);
    std::array<double, 600> oneHundredTwentyFps{};
    oneHundredTwentyFps.fill(1.0 / 120.0);
    constexpr double expectedDistance = 900.0;
    check(nearlyEqual(lab::simulate(thirtyFps), expectedDistance), "30 FPS travels 900 px");
    check(nearlyEqual(lab::simulate(sixtyFps), expectedDistance), "60 FPS travels 900 px");
    check(nearlyEqual(lab::simulate(oneHundredTwentyFps), expectedDistance), "120 FPS travels 900 px");
    const std::array unevenTimeline{0.010, 0.020, 0.005, 0.025, 0.040};
    check(nearlyEqual(lab::simulate(unevenTimeline), 18.0), "uneven 0.1-second timeline travels 18 px");
```


`simulate` gọi `update` đang dùng trong ứng dụng. Nếu ai đó đổi update về `/60`, trường hợp 60 FPS có thể còn đúng, nhưng 30/120 sẽ sai. Dãy không đều 0,1 s cho 18 px để tránh chỉ kiểm những khoảng thời gian đẹp.

### Bước 3 — Kiểm giới hạn dt và hướng chéo


```cpp title="tests/tests.cpp — hướng chéo đi qua công thức chuyển động"
lab::Vec2 diagonalPosition{};
    const lab::Vec2 diagonalVelocity = lab::velocityFromDirection(diagonal, 180.0);
    for (double dt : sixtyFps) {
        lab::update(diagonalPosition, diagonalVelocity, dt);
    }
    check(nearlyEqual(lab::length(diagonalPosition), expectedDistance), "keyboard diagonal travels 900 px");
```



```cpp title="tests/tests.cpp — dt lớn và thời gian âm"
lab::Vec2 position{};
    lab::update(position, {100.0, 0.0}, 0.2);
    check(nearlyEqual(position.x, 5.0), "large dt is clamped to 0.05 seconds");
    lab::update(position, {100.0, 0.0}, -1.0);
    check(nearlyEqual(position.x, 5.0), "negative dt is clamped to zero");
```


Bộ test đầy đủ còn có NaN, infinity và đúng điểm biên 0,05 s. Những trường hợp này không dùng để chứng minh tốc độ theo thời gian thật: chúng kiểm quy tắc **chủ động bỏ thời gian** đã chọn ở bài 4.

### Bước 4 — Kiểm hình chữ nhật và bộ giới hạn


```cpp title="tests/tests.cpp — đếm pixel, không chỉ nhìn hình"
lab::Framebuffer framebuffer;
    framebuffer.clear(0);
    lab::fillRectangle(framebuffer, 2, 3, 34, 34, 1);
    check(std::count(framebuffer.pixels.begin(), framebuffer.pixels.end(), 1u) == 34 * 34, "rectangle fills exactly width times height pixels");
    check(framebuffer.pixels[3 * lab::Framebuffer::width + 2] == 1, "rectangle includes top-left");
    check(framebuffer.pixels[3 * lab::Framebuffer::width + 36] == 0, "rectangle excludes right edge");
```


Đếm 34×34 phát hiện lỗi `<=` thay `<`. Kiểm riêng pixel cạnh phải phát hiện vẽ thừa sang ngoài. Các case tiếp theo trong file kiểm hình cắt qua mép trái/trên, phải/dưới, kích thước âm và tọa độ cực trị.


```cpp title="tests/tests.cpp — không thử underflow bằng một lệnh ngủ dài"
check(lab::remainingFrameNs(60, 4'000'000) == 12'666'666, "60 FPS sleeps only remaining budget");
    check(lab::remainingFrameNs(60, 20'000'000) == 0, "late frame never requests huge sleep");
    check(lab::remainingFrameNs(0, 0) == 0, "uncapped never divides by zero");
    check(lab::remainingFrameNs(-1, 0) == 0, "negative FPS is safely uncapped");
    check(lab::remainingFrameNs(120, 8'333'333) == 0, "exact budget requests no sleep");
```


Vì phần tính nghỉ tách khỏi SDL, ta kiểm kết quả 0 ngay lập tức thay vì làm chương trình thực sự ngủ quá lâu. Cách này giữ test nhanh và an toàn.

### Bước 5 — Kiểm điểm kết thúc phép đo năm giây


```cpp title="tests/tests.cpp — frame cuối được cắt đúng ở thời điểm năm giây"
measurement.start();
    for (int frame = 0; frame < 167; ++frame) {
        lab::advanceMeasurement(measurement, 0.03);
    }
    check(!measurement.running && nearlyEqual(measurement.elapsed, 5.0), "measurement clips final partial frame to five seconds");
    check(nearlyEqual(measurement.distance, 900.0), "measurement uses actual update for 900 px");
```


167 × 0,03 s vượt năm giây. Hàm phải chỉ nhận phần cần thiết của frame cuối, dừng ở 5,00 s và giữ kết quả không đổi ở các lần gọi sau. Các test tiếp theo còn kiểm restart và phần thời gian bị bỏ.

### Bước 6 — Build và chạy Debug/Release có giới hạn

Từ thư mục chứa `CMakeLists.txt` trong ZIP:

```bash title="Terminal — configure và test Debug"
cmake -S . -B build -DBUILD_CHECKPOINTS=ON -DBUILD_TESTING=ON
cmake --build build --config Debug --parallel 2
ctest --test-dir build -C Debug --output-on-failure --timeout 20
```

```bash title="Terminal — build và test Release"
cmake --build build --config Release --parallel 2
ctest --test-dir build -C Release --output-on-failure --timeout 20
```

Với Ninja/Makefiles, dùng hai thư mục build riêng và `-DCMAKE_BUILD_TYPE=Debug` hoặc `Release` khi configure. CTest không mở window và phải kết thúc nhanh; timeout 20 giây là hàng rào bảo vệ, không phải thời gian cần chờ bình thường.

```bash title="Terminal Windows — chạy bản hoàn chỉnh và smoke"
.\build\Debug\project_2_final.exe
.\build\Debug\project_2_final.exe --smoke
```

`--smoke` mở cửa sổ ẩn, dùng hướng chéo được script sẵn, chạy 12 frame có resize/upload/present rồi thoát. Khi tự động hóa, đặt deadline bên ngoài 15 giây để bảo vệ cả trường hợp driver kẹt. Nó không kiểm bàn phím vật lý hoặc độ chính xác FPS dài hạn.

## Ghép các phần lại

Mã nguồn hoàn chỉnh ở cuối trang chứa **toàn bộ file chạy được**, bao gồm CMake, framebuffer, presentation, chuyển động, phép đo và tests. Mỗi checkpoint là snapshot độc lập, không dùng macro ẩn chức năng của các bài sau. Trong repository website, chúng được sinh từ `source-template`; trong ZIP đã có sẵn.

Chạy bản final và thử theo thứ tự:

1. Giữ D rồi thả; thử A+D và W+D; đi tới cả bốn cạnh.
2. Chọn 1 rồi bấm B, giữ focus đến DONE. Lặp với 2, 3, 0 và ghi FPS, quãng đường tham chiếu, dropped. Khi dropped = 0, kết quả gần 900 px, sai lệch không quá 2%.
3. Nhấn F1 từng lần và giữ F1 để kiểm repeat không bật/tắt liên tục. R phải đặt lại cả vị trí lẫn các quãng đường.
4. Kéo resize, maximize, minimize/restore, chuyển sang cửa sổ khác rồi trở lại. Không méo hình, không nhảy bù toàn bộ thời gian bị tạm ngưng.
5. Thoát bằng Escape và Close ở hai lần chạy riêng.

Title `WASD` đo quãng đường player thực sự đi sau clamp; `TEST/DONE` đo vật tham chiếu không có biên. Đừng so hai con số như thể chúng luôn phải bằng nhau.

## Thử làm sai để hiểu đúng

1. Đổi hai phép cộng trong update về `velocity / 60`. Các test 30/120 FPS và dãy không đều phải thất bại.
2. Bỏ normalize ở `directionFromKeys`. Test keyboard diagonal phải thất bại, không chỉ một test normalize riêng lẻ.
3. Đổi dấu vòng lặp tô hình từ `<` thành `<=`. Test đếm pixel/cạnh phải phải phát hiện.
4. Bỏ nhánh `workNs >= targetNs` trong limiter. Chỉ chạy test hàm thuần; không đưa giá trị sai vào `SDL_DelayNS`.

Hoàn tác từng thay đổi trước khi chuyển sang thí nghiệm kế tiếp; chạy lại cả hai cấu hình.
