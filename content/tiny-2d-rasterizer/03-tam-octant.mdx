# Kéo hai đầu và soi từng pixel

## Vấn đề cần giải quyết

Sửa A/B rồi build lại giúp học thuật toán, nhưng không tiện để tìm lỗi. Ta cần kéo một đầu quanh đầu còn lại, đổi hướng ngay trên window và phóng to đoạn đang xem.

Checkpoint 3 thêm input và inspector cho **đường thẳng đã vẽ được**. Không đổi công thức DDA/Bresenham. Mục tiêu là quan sát được lỗi thay vì viết thêm một thuật toán chỉ để tạo hình minh họa.

## Hiểu ý tưởng trước khi viết code

Tám octant là tám vùng quanh A, phân bởi các trục và đường chéo. Một đoạn có thể đi trái/phải, lên/xuống và dốc cao/thấp. Hai trị tuyệt đối dx, dy xử lý độ dốc; stepX/stepY xử lý hướng. Không cần tám hàm Bresenham riêng.

Tọa độ chuột là một vấn đề khác. Ảnh luôn 960 × 540, nhưng window có thể lớn hơn, nhỏ hơn hoặc có dải letterbox. **Tọa độ event chưa phải chỉ số pixel của ảnh.** Ta phải đổi theo renderer rồi mới kiểm tra biên và floor.

Inspector cũng không tính lại “pixel đáng lẽ được vẽ”. Nó đọc 9 × 9 màu quanh pixel đang chọn từ framebuffer thật, sau đó vẽ mỗi màu thành một ô 16 × 16. Nhờ vậy, lỗi ghi ảnh vẫn có thể nhìn thấy dù công thức line đúng.

Chọn từng octant rồi đảo A/B. Mũi tên dịch B, Shift + mũi tên dịch A; PageUp/PageDown chọn bước. Trên màn hình, Y tăng xuống dưới nên thứ tự octant ở đây đi theo chiều kim đồng hồ từ phía phải/xuống.

## Viết code từng bước

### Bước 1 — Thêm trạng thái thao tác, không đặt nó trong thuật toán

Scene trong include/scene.hpp có các dữ liệu sau:


```cpp title="include/scene.hpp — hình học và thao tác đang thực hiện"
struct Scene {
    Point a{220, 270};
    Point b{740, 150};
    Algorithm algorithm = Algorithm::Bresenham;
    Tool tool = Tool::Line;
    int dragged = -1;
    bool zoom = true;
    std::size_t inspectedStep = 0;
    std::size_t octant = 0;
};
```

dragged = −1 nghĩa là chưa kéo; 0 chọn A, 1 chọn B. inspectedStep là chỉ số bản ghi, không phải tọa độ. zoom chỉ điều khiển phần hiển thị. Không trường nào trong số này thuộc công thức Bresenham.

Hàm sau nhận tọa độ **đã đổi về ảnh logic**:


```cpp title="include/scene.hpp — từ tọa độ logic đến một ô hợp lệ"
inline std::optional<Point> imagePoint(double x, double y) {
    if (!std::isfinite(x) || !std::isfinite(y) || x < 0.0 || y < 0.0 || x >= Framebuffer::width || y >= Framebuffer::height) {
        return std::nullopt;
    }
    return Point{static_cast<int>(std::floor(x)), static_cast<int>(std::floor(y))};
}
```

Điểm ngoài ảnh bị từ chối, không ép vào mép. Kiểm tra hữu hạn và biên trước phép đổi sang int. Trường hợp X = 960 nằm ngoài ảnh, còn 959,9 thuộc cột 959.

### Bước 2 — Chọn tay nắm gần nhất và giữ nó tới lúc thả


```cpp title="include/scene.hpp — bắt đầu một lần kéo"
inline bool beginDrag(Scene& scene, Point point) {
    if (scene.dragged >= 0 || !imagePoint(point.x, point.y)) {
        return false;
    }
    const Point second = secondHandle(scene);
    const double distanceA = std::hypot(static_cast<double>(point.x - scene.a.x), static_cast<double>(point.y - scene.a.y));
    const double distanceB = std::hypot(static_cast<double>(point.x - second.x), static_cast<double>(point.y - second.y));
    scene.dragged = 1;
    if (distanceA <= distanceB) {
        scene.dragged = 0;
    }
    moveHandle(scene, point);
    return true;
}
```

Ta dùng khoảng cách để chọn A hoặc B; nếu bằng nhau, ưu tiên A. secondHandle hiện trả B, về sau công cụ circle sẽ dùng vị trí tay nắm bán kính.

Lần nhấn đầu cũng gọi moveHandle để điểm phản hồi ngay tại nơi click:


```cpp title="include/scene.hpp — thay đổi tay nắm đã chọn"
inline void moveHandle(Scene& scene, Point point) {
    if (scene.dragged < 0 || !imagePoint(point.x, point.y)) {
        cancelDrag(scene);
        return;
    }
    if (scene.dragged == 0) {
        scene.a = point;
    } else {
        {
            scene.b = point;
        }
    }
    scene.inspectedStep = 0;
}
```

Khi kéo xong:


```cpp title="include/scene.hpp — giữ cả tọa độ chỉ xuất hiện ở sự kiện thả nút"
inline void endDrag(Scene& scene, Point point) {
    moveHandle(scene, point);
    cancelDrag(scene);
}
```

Giống Mini Paint, vị trí cuối không nhất thiết xuất hiện trong một motion trước đó. endDrag cập nhật vị trí rồi mới hủy trạng thái kéo. Ngược lại, mất focus hoặc pointer bị hủy chỉ cần cancelDrag, không tự tạo một vị trí cuối.

### Bước 3 — Đổi tọa độ event đúng một lần

Trong main, trước khi đọc event.button hoặc event.motion:


```cpp title="src/main.cpp — đổi tọa độ mouse theo renderer"
const bool mouseEvent = event.type == SDL_EVENT_MOUSE_BUTTON_DOWN || event.type == SDL_EVENT_MOUSE_BUTTON_UP || event.type == SDL_EVENT_MOUSE_MOTION;
if (mouseEvent && !SDL_ConvertEventToRenderCoordinates(renderer, &event)) {
    std::cerr << "Mouse coordinates: " << SDL_GetError() << '\n';
    failed = true;
    running = false;
    break;
}
```

SDL_ConvertEventToRenderCoordinates tính cả logical presentation, scale và viewport. [Tài liệu SDL](https://wiki.libsdl.org/SDL3/SDL_ConvertEventToRenderCoordinates) lưu ý kết quả vẫn có thể nằm ngoài vùng render; vì thế imagePoint vẫn cần thiết.

Không vừa gọi hàm này vừa tự nhân theo tỉ lệ window. Như vậy sẽ đổi tọa độ hai lần, khiến tay nắm lệch khi resize hoặc trên màn hình HiDPI.

Phần event còn lại của checkpoint làm các việc cụ thể:

- Down chỉ nhận nút trái; beginDrag thành công mới lưu MouseID và yêu cầu capture.
- Motion chỉ nhận đúng MouseID đang kéo, đồng thời kiểm tra SDL_BUTTON_LMASK. Mẫu ngoài ảnh hoặc không còn giữ nút sẽ hủy kéo.
- Up cùng thiết bị gọi endDrag để lấy điểm cuối rồi nhả capture.
- Mất focus, minimize, resize hoặc rời window đều kết thúc kéo. Quay lại khi còn giữ nút không tự bắt đầu một lần kéo mới.

Capture có thể không được driver hỗ trợ. Chương trình ghi cảnh báo nhưng vẫn dùng các event nhận được; nó không giả vờ rằng đã kiểm được capture vật lý. Xem thêm [SDL_CaptureMouse](https://wiki.libsdl.org/SDL3/SDL_CaptureMouse).

### Bước 4 — Tạo bộ tám hướng cố định để lặp lại lỗi


```cpp title="include/scene.hpp — phím O đổi octant"
inline void selectOctant(Scene& scene) {
    constexpr std::array<Point, 8> offsets{{
        {9, 2},
        {2, 9},
        {-2, 9},
        {-9, 2},
        {-9, -2},
        {-2, -9},
        {2, -9},
        {9, -2},
    }};
    cancelDrag(scene);
    scene.tool = Tool::Line;
    scene.a = {480, 270};
    const Point offset = offsets[scene.octant];
    scene.b = {scene.a.x + offset.x * 22, scene.a.y + offset.y * 22};
    scene.octant = (scene.octant + 1) % offsets.size();
    scene.inspectedStep = 0;
}
```

Độ lệch (9,2), (2,9), … được nhân 22 để nhìn rõ trên ảnh lớn. A luôn trở về (480,270); octant chạy từ 0 tới 7 rồi lặp. Bộ dữ liệu cố định giúp bạn nói chính xác “lỗi ở hướng thứ tư” thay vì cố kéo chuột giống lần trước.

D/B vẫn đổi thuật toán. 1 về Line; I/J/K/L dịch B một pixel, giữ Shift để dịch A. Ta không dùng WASD ở đây vì D đã dành cho DDA. Mũi tên trái/phải chọn bước, Home/End chọn bản ghi đầu/cuối; Z bật/tắt inspector.

Mỗi lệnh hoặc thay đổi hình học đều kết thúc thao tác kéo đang có. Bạn không thể tiếp tục điều khiển A bằng một lần nhấn chuột cũ sau khi đã đổi công cụ bằng bàn phím.

### Bước 5 — Phóng to dữ liệu màu thật

Đây là phần đọc và vẽ inspector trong include/view.hpp:


```cpp title="include/view.hpp — inspector 9 × 9 lấy từ framebuffer"
inline void drawInspector(Framebuffer& framebuffer, Point selected) {
    constexpr int kCells = 9;
    constexpr int kCellSize = 16;
    constexpr int kOriginX = 800;
    constexpr int kOriginY = 380;
    std::array<std::uint32_t, kCells * kCells> source{};

    // Chụp vùng nguồn trước khi vẽ overlay để không tự đọc pixel vừa phóng to.
    for (int row = 0; row < kCells; ++row) {
        for (int column = 0; column < kCells; ++column) {
            const int x = selected.x + column - kCells / 2;
            const int y = selected.y + row - kCells / 2;
            std::uint32_t color = kBackground;
            if (imagePoint(x, y)) {
                color = framebuffer.pixels[static_cast<std::size_t>(y) * Framebuffer::width + x];
            }
            source[static_cast<std::size_t>(row * kCells + column)] = color;
        }
    }

    for (int row = 0; row < kCells; ++row) {
        for (int column = 0; column < kCells; ++column) {
            std::uint32_t border = 0x39445FFFu;
            if (column == kCells / 2 && row == kCells / 2) {
                border = kSelectedColor;
            }
            for (int dy = 0; dy < kCellSize; ++dy) {
                for (int dx = 0; dx < kCellSize; ++dx) {
                    std::uint32_t color = border;
                    if (dx > 0 && dy > 0) {
                        color = source[static_cast<std::size_t>(row * kCells + column)];
                    }
                    framebuffer.putPixel(kOriginX + column * kCellSize + dx, kOriginY + row * kCellSize + dy, color);
                }
            }
        }
    }
}
```

Có hai lượt duyệt tách biệt. Lượt đầu chụp 81 màu vào source. Lượt sau mới vẽ overlay tại góc dưới phải. Nếu đọc/ghi xen kẽ, khi vị trí đang soi nằm gần overlay, các ô cuối có thể đọc nhầm chính ảnh vừa phóng to.

Màu viền cam đánh dấu ô trung tâm; phần trong ô vẫn là màu gốc. Các tọa độ ngoài ảnh dùng màu nền. Marker tay nắm được vẽ sau inspector, nên bạn đang soi hình học trước khi marker che pixel đó.

Tiêu đề đọc cùng frame.line[inspectedStep] mà plotSteps đã dùng. Với DDA, nó hiện tọa độ liên tục; với Bresenham là error/e2 và hai quyết định trục. Khi tắt zoom, đường vẫn vẽ đầy đủ: thao tác chọn bước chỉ dùng để quan sát, không chạy một bản thuật toán khác.

## Ghép các phần lại

Input đổi tọa độ → Scene thay A/B → dirty tạo lại SceneFrame → ghi ảnh line → chụp vùng inspector → vẽ overlay/tay nắm → upload/present. Bresenham vẫn là vòng lặp của bài 2.

Kéo một đầu xuyên qua đầu kia, thử tất cả octant, rồi giảm khoảng cách tới mức hai đầu trùng nhau. Đọc số bản ghi và pixel được chọn trong tiêu đề, thay vì chỉ nhìn đường có vẻ đẹp.

## Thử làm sai để hiểu đúng

1. Đọc event.button.x trực tiếp như pixel ảnh. Resize window sang tỉ lệ khác, click nơi có tay nắm và quan sát độ lệch; hoàn tác trước khi thử tiếp.
2. Bỏ xử lý vị trí trong endDrag. Thử thả chuột ở vị trí chưa có motion tương ứng; điểm có thể dừng ở mẫu trước.
3. Bỏ nhánh kiểm SDL_BUTTON_LMASK. Nếu một sự kiện thả nút bị mất, các motion sau có thể tiếp tục kéo dù nút đã nhả.
4. Trong inspector, đọc trực tiếp framebuffer khi đang vẽ từng ô thay vì chụp source trước. Soi gần góc dưới phải và tìm dấu hiệu overlay tự lặp.

## Tự kiểm tra kết quả

- Kéo được cả A lẫn B; đúng MouseID mới điều khiển lần kéo đang có.
- Rời ảnh, mất focus, resize và thả nút không để lại trạng thái kéo.
- O đi đủ tám hướng; DDA/Bresenham giữ hai đầu và liên thông theo cả hai chiều.
- Z và mũi tên không thay dữ liệu thuật toán; inspector đọc ảnh thật và không tự đọc overlay.
- Resize khác tỉ lệ và HiDPI, nếu có, vẫn chọn đúng vị trí trên ảnh. Việc này phải thử trên desktop, không suy từ CTest.

## Bài tập mở rộng

Lưu lại hai bộ pixel của đoạn (0,0) → (2,1) và chiều ngược. Cả hai có hai đầu và khoảng cách bước hợp lệ, nhưng không nhất thiết cùng pixel giữa. Viết tiêu chí kiểm tra dựa trên khoảng cách tới đường lý tưởng thay vì buộc đảo chiều phải cho cùng một tập.
