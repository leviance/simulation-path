# Đo cả những lần SoA chậm hơn

## Vấn đề cần giải quyết

Ở bài trước, một phép tính trên giấy cho thấy: để lấy 64 vận tốc dọc, SoA chỉ chạm 4 cache line thay vì 44. Thế liệu cứ đổi sang SoA là đài phun sẽ nhanh hơn? Ta đã bỏ qua một chi tiết: khi giọt hết tuổi, CPU không chỉ đọc vận tốc dọc. Nó cần biết tuổi, vị trí, thế hệ, hướng phóng và phải ghi lại cả hạt mới.

Hãy viết ra dự đoán cho **từng** workload trước khi đo. Cuối bài ta cần một kết luận có điều kiện, chẳng hạn “nhanh hơn khi chỉ sửa vận tốc dọc ở quy mô này”, không phải khẩu hiệu “SoA thắng”.

## Hiểu ý tưởng trước khi viết code

Gọi A là AoS, B là SoA. Cả hai nhận cùng một bản hạt ban đầu, cùng $dt$, cùng ba lượt qua đủ mảng. Nếu luôn chạy A rồi B, phía sau có thể được hưởng lợi hoặc chịu thiệt chỉ vì chạy sau. Vì vậy ta đổi thứ tự **AB/BA** qua các mẫu. Đây không phải cách loại bỏ mọi nhiễu: chương trình **không flush cache**, hệ điều hành vẫn có việc khác, compiler có thể vector hóa hai vòng lặp khác nhau.

Ba quy mô 10.000, 100.000 và 1.000.000 hạt nhân với hai workload cho sáu ca. Mỗi ca có một lượt làm nóng rồi năm mẫu cho mỗi bên. Đồng hồ đo tổng ba pass trong một mẫu; đổi sang ms/pass cho *cả hai* nếu muốn so ở đơn vị khác.

## Viết code từng bước

### Luân phiên thứ tự nhưng không đổi dữ liệu

{/* snippet include/benchmark.hpp#trial-order */}
```cpp title="include/benchmark.hpp — Chọn bên chạy trước, đặt các bộ đếm về đầu"
void chooseMethod() {
    // Method 0 is AoS, method 1 is SoA. Odd samples reverse the pair.
    method = 0;
    if (paired) {
        const bool soaFirst = sample >= 0 && sample % 2 == 1;
        if (soaFirst)
            method = 1 - trial;
        else
            method = trial;
    }
    target = 0;
    step = 0;
    trialUpdated = 0;
    kernelMs = 0;
    phase = BenchmarkPhase::reset;
}
```

`trial` chọn lượt đầu hay lượt sau trong cặp; `sample` cho biết đang ở mẫu nào. Bất kể bên nào chạy trước, `resetUnit` luôn chép từ cùng `initial`. Nếu cho SoA bắt đầu từ *kết quả* AoS vừa tính thì hạt đã già đi ba bước, không còn là cùng một bài toán.

{/* snippet include/benchmark.hpp#benchmark-kernel-unit */}
```cpp title="include/benchmark.hpp — Cả hai nhánh đi qua cùng một khoảng chỉ số"
void kernelUnit() {
    const std::size_t end = std::min(row.count, target + 4096);
    const auto started = Clock::now();
    if (method == 0) {
        updateAoSRange(workAoS, target, end, config, fixedDt, row.workload, row.count);
    }
    else {
        updateSoARange(workSoA, target, end, config, fixedDt, row.workload, row.count);
    }
    kernelMs += milliseconds(started);
    trialUpdated += end - target;
    target = end;
    if (target != row.count)
        return;
    target = 0;
    if (++step < 3)
        return;
    if (trialUpdated != row.count * 3)
        throw std::runtime_error("Incomplete benchmark pass");
    row.updated = trialUpdated;
    if (sample >= 0) {
        if (method == 0)
            aosTimes.push_back(kernelMs);
        else
            soaTimes.push_back(kernelMs);
    }
    ++trial;
    int methodsPerSample = 1;
    if (paired) {
        methodsPerSample = 2;
    }
    if (trial < methodsPerSample)
        chooseMethod();
    else {
        row.checksumAoS = row.checksumSoA = 0;
        phase = BenchmarkPhase::verify;
    }
}
```

### Kiểm kết quả trước khi nhìn hai cột thời gian

{/* snippet include/benchmark.hpp#verify-pair */}
```cpp title="include/benchmark.hpp — Đối chiếu từng ô sau khi tắt đồng hồ"
for (std::size_t index = target; index < end; ++index) {
    const auto& first = workAoS[index];
    if (first.id != index || !finiteParticle(first))
        throw std::runtime_error("AoS state validation failed");
    row.checksumAoS += particleChecksum(first);
    const ParticleAoS second = readParticle(workSoA, index);
    row.checksumSoA += particleChecksum(second);
    row.maximumDifference = std::max(row.maximumDifference, particleDifference(first, second));
    row.maximumErrorRatio = std::max(row.maximumErrorRatio, particleErrorRatio(first, second));
}
```

Phép so từng trường ở bài 05 nay làm trọng tài. Cộng hai checksum để kết quả phải được dùng, rồi xét tỉ số sai số lớn nhất và ID cho từng cặp. Nếu một bên tính thiếu hạt hoặc sinh sai thế hệ, đừng đưa thời gian đó vào bảng speedup. Phần chuẩn bị mảng đầu vào, sao chép, chuyển layout và kiểm đầu ra vẫn nằm ngoài thời gian kernel.

## Ghép các phần lại

```bash title="Terminal — đo từ chính bản Release vừa viết"
cmake --build build-work --config Release --target project_32_work --parallel 1
.\build-work\Release\project_32_work.exe --benchmark
```

Dưới đây là bốn dòng trích từ một lượt đo **chính đài phun trong ZIP**, trên AMD Ryzen 5 5600H, Windows x64, MSVC 19.33, C++20, Release (`/O2 /Ob2 /DNDEBUG`), một luồng, không dùng SIMD thủ công. Cả hai bên bắt đầu với seed `0x32c0ffee`, $dt=1/120$ s, cùng một vòi phun. Đơn vị là **ms cho ba pass**; số trong ngoặc là [min–max] của năm mẫu sau lượt làm nóng.

| --- | --- | --- |
| 10.000 / gravity-only | 0,0175 [0,0172–0,0228] | 0,0021 [0,0021–0,0022] |
| 10.000 / full lifecycle | 0,0648 [0,0644–0,0679] | 0,1326 [0,1323–0,1332] |
| 1.000.000 / gravity-only | 31,3545 [26,6993–48,3400] | 1,0548 [0,5800–3,1566] |
| 1.000.000 / full lifecycle | 27,6026 [25,2939–34,6756] | 47,6417 [47,2939–48,5732] |

Hãy đọc hai hàng cuối cạnh nhau. Cũng một triệu hạt trên máy này, SoA nhanh hơn khi chỉ sửa `velocityY`, nhưng lại **chậm hơn** khi cập nhật cả vòng đời. Ở ca vòng đời, hai checksum đều là `5.98369e7`, sai khác lớn nhất giữa các trường bằng 0: không phải AoS nhanh nhờ bỏ qua công việc. Những số này đo vòng cập nhật trên một máy ở một lần chạy, không phải số ms để hiển thị một khung hình hay lời hứa cho máy khác.

Khi ghi kết quả của bạn, lưu cả sáu dòng, kể cả dòng trái dự đoán. Ghi tên CPU, hệ điều hành, compiler, các cờ Release trong `build-work/CMakeCache.txt`, tải nền và có dùng lệnh SIMD thủ công hay không (project này không dùng). Nếu muốn khẳng định một chênh lệch *do* compiler vector hóa, cần thêm báo cáo tối ưu hoặc profiler; bảng thời gian chưa cho biết nguyên nhân đó.

## Thử làm sai để hiểu đúng

1. Thử cho SoA chỉ đi một pass trong khi AoS đi ba. Một tỉ số rất đẹp vẫn vô nghĩa: số lượt thực phải làm phép đo bị loại. Trả cả hai về ba pass trước khi thu lại dữ liệu.
2. Giả sử chỉ cần xử lý một bước rồi đổi ngay về AoS để vẽ. So chi phí “chỉ update” với “đổi đi + update + đổi về”. Nếu hai kết luận khác nhau, bạn vừa tìm được chi phí quyết định có nên đổi layout trong ứng dụng thật; đừng cộng conversion cho riêng một bên rồi gọi đó là kernel.

## Tự kiểm tra kết quả

- Có sáu ca native hoặc ghi rõ đã hủy/hết hạn, không điền số cho ca còn thiếu.
- Mỗi bên chạy đủ ba lượt qua N hạt, tính được checksum và qua phép đối chiếu từng trường.
- Giải thích được một kết quả nhanh hơn và một kết quả không nhanh hơn mà không gọi mô hình cache line là số đo phần cứng.
- Kết quả JavaScript của Canvas chỉ để học quy trình, không thay số native ở bảng này.

## Bài tập mở rộng

Giả sử chuyển sang SoA có chi phí $C$ ms nhưng tiết kiệm được $d$ ms mỗi bước. Khi $d>0$, cần ít nhất bao nhiêu bước mới bù được $C$? Nếu còn phải đổi về AoS ở cuối, đưa cả hai chi phí đổi vào tử số. Với dòng có $d\leq0$, phép chia không cho một mốc hòa vốn dương có nghĩa.
