# CPU phải đọc bao nhiêu để sửa một con số?

## Vấn đề cần giải quyết

Hãy nhìn vào vòng cộng trọng lực: nó chỉ sửa một số thực, `velocityY`, cho mỗi giọt. Vậy nếu có 64 giọt, cả hai cách lưu đều sửa đúng 256 byte. Tại sao chúng vẫn có thể mất thời gian khác nhau?

Đặt hình đài phun sang một bên trong ít phút. Việc của bài này là đánh dấu **những vùng địa chỉ** chứa 64 con số ấy. Ta chưa đo tốc độ và cũng không đọc được bộ đếm cache miss của phần cứng từ phép tính này.

## Hiểu ý tưởng trước khi viết code

Hãy kẻ các vạch tại byte 0, 64, 128, 192…; mỗi khoảng là một `cache line` của mô hình. Ta **giả sử** mảng bắt đầu đúng một vạch (aligned base). Với AoS, mỗi hạt chiếm 44 byte; trong struct này, `velocityY` ở byte 24. Với SoA, cột `velocityY` là một dãy `float` liền nhau bắt đầu từ byte 0.

| Hạt | Byte chứa `velocityY` ở AoS | Line AoS | Byte chứa `velocityY` ở SoA | Line SoA |
| --- | ---: | ---: | ---: | ---: |
| 0 | 24 | 0 | 0 | 0 |
| 1 | 68 | 1 | 4 | 0 |
| 2 | 112 | 1 | 8 | 0 |
| 3 | 156 | 2 | 12 | 0 |

Hạt 1 và 2 ở AoS chung một line, nên đếm **mỗi hạt một line** sẽ sai. Hãy thử kéo dài bảng tới hạt 63: với SoA, cứ 16 vận tốc mới sang vạch tiếp theo. Bạn có cần xem hình đài phun hoặc chạy đồng hồ để trả lời câu hỏi về địa chỉ này không?

## Viết code từng bước

### Chọn ba số cần trả về

{/* snippet include/benchmark.hpp#traffic-fields */}
```cpp title="include/benchmark.hpp — Ba đại lượng để đọc kết quả bằng đúng đơn vị"
struct TrafficModel {
    std::size_t usefulBytes{}, uniqueLines{}, loadedBytes{};
    bool upperBound{};
};
```

`usefulBytes` đếm các byte chứa trường cần dùng, `uniqueLines` đếm bao nhiêu khối địa chỉ khác nhau chứa chúng, còn `loadedBytes` là dung lượng **suy ra từ mô hình** bằng số line nhân 64. Tên `loadedBytes` không biến nó thành lượng dữ liệu thực tế đã đi qua RAM. Cờ `upperBound` sẽ nhắc ta khi nào chỉ có một cận trên.

### Dùng kích thước và độ dời của chính kiểu C++

{/* snippet include/benchmark.hpp#model-traffic */}
```cpp title="include/benchmark.hpp — Lần theo địa chỉ chứ không đếm cache miss"
inline TrafficModel modelTraffic(std::size_t count, Layout layout, MemoryWorkload workload) {
    if (count > maximumParticles)
        throw std::invalid_argument("Traffic model budget");
    if (count == 0)
        return {};
    TrafficModel result{};
    if (workload == MemoryWorkload::gravityOnly) {
        result.usefulBytes = count * sizeof(float);
        if (layout == Layout::aos) {
            const std::size_t offset = offsetof(ParticleAoS, velocityY);
            result.uniqueLines = (offset + (count - 1) * sizeof(ParticleAoS)) / 64 + 1;
        } else
            result.uniqueLines = (count * sizeof(float) + 63) / 64;
    } else {
        // Upper bound assuming all eleven fields are touched. Real respawn
        // touches ID/generation/hue selectively; this is not a cache-miss count.
        result.upperBound = true;
        result.usefulBytes = count * sizeof(ParticleAoS);
        if (layout == Layout::aos) {
            result.uniqueLines = (result.usefulBytes + 63) / 64;
        } else {
            result.uniqueLines = 11 * ((count * sizeof(float) + 63) / 64);
        }
    }
    result.loadedBytes = result.uniqueLines * 64;
    return result;
}
```

`offsetof(ParticleAoS, velocityY)` lấy độ dời từ kiểu thực tế thay vì viết cứng 24. Trong AoS, hai địa chỉ liên tiếp cách 44 byte, nhỏ hơn một line; vì thế từ line đầu đến line cuối không có line trống bị nhảy qua. Ở SoA, tính số line cho $4N$ byte liên tiếp bằng phép chia làm tròn lên. Trường hợp $N=0$ phải trả 0 trước khi dùng $N-1$.

Còn khi tiến trọn vòng đời, hạt đang bay không phải lúc nào cũng cần đọc ID, thế hệ hay màu. Đếm đủ mười một trường là **cận trên** của số line trong mô hình giả định, không phải lời hứa rằng CPU sẽ đọc đủ số byte ấy từ RAM.

### Đối chiếu với bài tính tay

{/* snippet tests/tests.cpp#traffic-64 */}
```cpp title="tests/tests.cpp — Một ca có thể kiểm bằng bút và giấy"
const auto aos = lab::modelTraffic(64, lab::Layout::aos, lab::MemoryWorkload::gravityOnly);
const auto soa = lab::modelTraffic(64, lab::Layout::soa, lab::MemoryWorkload::gravityOnly);
check(aos.usefulBytes == 256 && aos.uniqueLines == 44 && soa.uniqueLines == 4, "hand-counted 64B aligned-base model");
```

Trước khi xem kết quả trên cửa sổ, tự làm phép chia cuối: byte $24+63\cdot44=2796$ nằm ở line 43. Tính cả line số 0, AoS chạm **44 line**; SoA chạm **4 line**. Cả hai đều dùng đúng 256 byte hữu ích. Fixture này có sẵn trong gói để kiểm bản hoàn thiện, không phải đoạn dán vào vòng lặp C++.

Trong `work/include/application.hpp`, đưa kết quả `modelTraffic` vào phần báo cáo, đặt giả định “64 B, aligned base” cạnh số liệu. Không ghi nhãn `cache misses` cho `uniqueLines`.

## Thử làm sai để hiểu đúng

1. Thay khoảng cách giữa hai `velocityY` ở AoS bằng `sizeof(float)`. Ca 64 hạt bỗng báo 4 line ở cả hai bên. Vẽ lại địa chỉ hạt số 1 trên bảng để tìm sai lầm, rồi trả stride về `sizeof(ParticleAoS)`.
2. Trên giấy, dịch điểm bắt đầu của cột SoA sang byte 32. 64 số thực liên tiếp giờ trải từ byte 32 tới 287, chạm **5** line. Công thức ban đầu không bỗng sai; bạn vừa thay giả định căn hàng. Đừng sửa fixture cũ thành 5.

## Tự kiểm tra kết quả

- Tính lại được trường hợp 64 hạt bằng địa chỉ và giải thích vì sao 44/4 **không** phải dự đoán SoA nhanh gấp 11 lần.
- Với N bằng 0, không có line nào được tính; với full lifecycle, báo cáo ghi rõ đây là cận trên.
- Nhận biết giới hạn: cache line có thể đã nằm trong cache, allocator có thể đặt mảng lệch biên, compiler có thể tối ưu hai vòng lặp khác nhau.

## Bài tập mở rộng

Tính số line cho cột `velocityY` khi N tăng từ 16 lên 17. Dự đoán cách tăng của SoA và của AoS trên cùng đồ thị. Sang bài sau ta sẽ đặt kết quả đo Release cạnh giả thuyết này; đừng sửa giả thuyết sau khi đã thấy số đo.
