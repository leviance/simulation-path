# Đi một vòng và kiểm tra bản hoàn chỉnh

## Vấn đề cần giải quyết

Trước khi bỏ bớt mặt ở Project 59, hãy chắc rằng bản chưa tối ưu đã đúng. Lỗi sinh thiếu một mặt và lỗi vẽ một mặt phía sau lên trước có thể tạo cùng một lỗ đen trên ảnh, nhưng cần hai phép kiểm khác nhau.

## Hiểu ý tưởng trước khi viết code

Dành một lượt kiểm dữ liệu và một lượt tự đi trong chương trình. Một ảnh đẹp không cho biết mảng có đúng 4.096 ô, cũng như một bảng PASS không cho biết camera có thật sự bước vào cảnh được hay không.

## Viết code từng bước

Trước khi tối ưu, hãy lưu một mốc đủ tin cậy để sau này biết mình đã bỏ đúng mặt. Ta sẽ viết phép kiểm ngay trong ứng dụng, rồi chạy tests trên chính mã đã viết.

### Tạo ba cảnh cực nhỏ thay vì đếm bằng mắt

Thêm `inspectFixtures` và chuỗi kết quả vào `scene.hpp`. Dùng đúng `naiveMesh` của mình dựng cột rỗng, một viên và cột đặc; báo lỗi nếu số quad khác 0, 6, 24.576. Đừng lấy số trên HUD rồi so với chính nó.

{/* snippet include/trail/scene.hpp#audit-fixtures */}

```cpp title="include/trail/scene.hpp — Ba mốc hình học phải đúng trước khi tối ưu"
void inspectFixtures() {
    const Mesh full = naiveMesh(solidCube());
    const Mesh empty = naiveMesh(Column{});
    const Mesh single = naiveMesh(singleStone());
    if (full.size() != 24576 || !empty.empty() || single.size() != 6) {
        throw std::runtime_error("Unexpected baseline mesh");
    }
    auditResult = "PASS: empty 0 / stone 6 / solid 24576 quads";
}
```

### Cho phép gọi phép kiểm khi đang đi

Trong `window.hpp`, phím V gọi `scene.inspectFixtures()` và bật bảng số. Khi bảng đang mở, in kết quả nếu chuỗi không rỗng. Phép chiếu dưới đây là phần dùng lại: đổi kích thước ảnh chỉ đổi kích thước biểu kiến, không thể đổi số quad của fixture.

{/* snippet include/trail/camera.hpp#perspective-scale */}

```cpp title="include/trail/camera.hpp — Kiểm kích thước bằng FOV cố định"
inline double focalLength(int imageHeight, double verticalFov) {
    return 0.5 * imageHeight / std::tan(verticalFov * 0.5);
}
```

## Ghép các phần lại

Nhấn V trên bản của bạn, đọc cả ba số rồi bật H để so một lớp ở bờ suối. Thử đổi số mong đợi của viên đá thành 5: phép kiểm phải báo sai. Khôi phục lại 6 rồi mới chạy Debug và Release bên dưới.

```bash title="Terminal — chạy bản bạn vừa viết"
cmake --build build-work --config Release --target project_58_work --parallel 1
.\build-work\Release\project_58_work.exe
```

## Thử làm sai để hiểu đúng

So khối đặc với hai viên kề nhau. Nếu bản chưa tối ưu báo 20 tam giác thay vì 24 cho cặp viên, bạn đã đưa thuật toán của Project 59 vào mốc đo ban đầu.

## Tự kiểm tra kết quả

Kiểm CTest cả Debug và Release; sau đó mở chương trình có cửa sổ và tự đi, quay nhìn lên/xuống, trả chuột bằng Esc. Các tầng test này trả lời những câu hỏi khác nhau.


Khi bản của bạn đã đủ các tính năng, chạy bộ kiểm của project trên chính `work/include`. Dùng lại thư mục `build-work` đã cấu hình với `VOXEL_WORKBOOK=ON`; chạy test của bản mẫu trong thư mục khác không kiểm được mã này.

```bash title="Windows / Visual Studio — kiểm bài làm ở cả hai cấu hình"
cmake --build build-work --config Debug --target project_58_tests --parallel 1
ctest --test-dir build-work -C Debug --output-on-failure --timeout 30
cmake --build build-work --config Release --target project_58_tests --parallel 1
ctest --test-dir build-work -C Release --output-on-failure --timeout 30
```

Với Ninja/Make, kiểm Release trong `build-work`. Để kiểm Debug thật, cấu hình thêm `cmake -S . -B build-work-debug -DVOXEL_WORKBOOK=ON -DCMAKE_BUILD_TYPE=Debug` rồi dùng `build-work-debug` cho hai lệnh Debug. Cả hai đọc cùng một thư mục `work/`.
